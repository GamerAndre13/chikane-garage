FASE 0 — CONTEXTO DO PROJETO E OBJETIVOS
--------------------------------------------------------------------------------

O QUE É
-------
A Chikane Garage é uma garagem/stand online especializada em viaturas diesel
BMW de PERFORMANCE, importadas da Europa (Alemanha, Bélgica, Holanda) e
entregues em Portugal com garantia. A identidade é "de nicho": não é um stand
convencional — é uma garagem privada que seleciona, inspeciona (140 pontos de
verificação), documenta com transparência e entrega com garantia Chikane.

OBJETIVOS DO PROJETO
--------------------
1. Lançar um site público profissional que apresente o catálogo de viaturas,
   a história/processo da garagem, uma loja de acessórios e um formulário de
   contacto/test drive.
2. Funcionar como um "backoffice" para o proprietário gerir conteúdo:
   - Viaturas (CRUD completo, galeria de fotos, specs técnicas, estado).
   - Produtos da loja (CRUD).
   - Pedidos de contacto e test drives recebidos (gerir estados).
   - Conteúdo do site (CMS simples por secção).
   - Estatísticas/Analytics do stock.
3. Apoiar utilizadores registados:
   - Conta própria (perfil, password, avatar).
   - Guardar viaturas favoritas (local sem login / base de dados com login).
   - Ver os próprios pedidos de contacto e test drives.
4. Ser fácil de manter e de colocar em produção (Next.js + Supabase + Cloudflare).

STACK E TECNOLOGIAS
-------------------
- Framework: Next.js 16.3.4 (App Router, React 19.2.8).
- Linguagem: TypeScript (strict).
- Estilo: Tailwind CSS v4 (via @tailwindcss/postcss) + CSS vars customizadas
  (tema escuro + cobre).
- Fontes: Google Fonts via next/font — Oswald (display) + Inter (sans).
- Backend/BD/Auth: Supabase (PostgreSQL + Auth + Storage com RLS).
- Armazenamento de imagens: Cloudflare R2 (S3-compatible) — galerias e avatares.
  @aws-sdk/client-s3 + @aws-sdk/s3-request-presigner.
- Deploy: Cloudflare (Workers via OpenNext — @opennextjs/cloudflare). Houve uma
  transição Vercel/standalone → Cloudflare (ver Fase G).

COMO FOI FEITO
--------------
O schema foi desenhado em scripts SQL dentro de supabase/, para serem corridos
manualmente no SQL Editor do Supabase. Há 6 ficheiros:

1) setup.sql (446 linhas) — O schema V2, mais completo e estruturado.
   Contém 10 tabelas com RLS, triggers, grants e storage. É o ficheiro
   CANÓNICO atual. Tabelas:
   - profiles        — Perfil do user ligado a auth.users (id FK). role
                       ('user'/'admin'), full_name, phone, avatar_url, email.
                       Trigger handle_new_user cria profile no registo.
   - vehicles        — Tabela principal de viaturas com TODOS os campos:
                       identificação (brand/model/trim/reg_year/reg_month/status),
                       specs (engine/power/torque/transmission/drivetrain/fuel/
                       consumption/co2/cor/quilometragem),
                       histórico (previous_owners/service_book/accident_*/
                       last_service/tires_condition),
                       origem (origin/origin_country/coc_confirmed/isv_paid/
                       legalization_date),
                       comercial (price/financing/warranty/trade_in),
                       media (cover_image_url/video_url),
                       meta (description/is_featured/published_at/timestamps).
                       Slugs únicos. RLS: leitura pública, escrita só admin.
   - vehicle_features — Extras/equipamento por viatura (label).
   - vehicle_images   — Galeria (url, position, alt_text; FK veic. CASCADE).
   - shop_products    — Produtos da loja (name, slug, price, stock, active...).
   - favorites        — Favoritos (user_id × vehicle_id, UNIQUE juntos).
   - contact_requests — Pedidos de info (status new/read/confirmed/archived).
   - test_drives      — Test drives (vehicle_id, user_id, preferred_date/time,
                       status pending/confirmed/completed/cancelled).
   - site_content     — CMS de textos (section_key UNIQUE + title/subtitle/
                       body/image_url/link_url/link_text).
   - site_settings    — Definições globais (phone/email/address/location/sociais).
   RLS: leitura pública nas tabelas públicas; escrita/gestão só admin;
   contactos/test drives inseríveis por anon (posteriormente refinado).
   Storage: bucket 'avatars' público + policies.

2) 002_full_site.sql (238 linhas) — Schema V1 ANTIGO (mais simples, colunas
   diferentes: year, featured, vehicle_slug em vez de vehicle_id, site_settings
   em formato key/value). MANTIDO por histórico, mas NÃO é o schema atual.

3) favorites.sql (32 linhas) — Criação isolada da tabela favorites + RLS.

4) newsletter.sql (50 linhas) — Tabela newsletter_subscribers (email UNIQUE,
   status active/unsubscribed), RLS: select/update/delete só admin, insert
   anon. Inclui honeypot anti-bot no front.

5) migracao_perfil_e_fotos.sql (117 linhas) — Migração que:
   - (re)cria a newsletter.
   - adiciona contact_requests.user_id (FK auth.users, ON DELETE SET NULL)
     para ligar pedidos ao user.
   - RLS dos contact_requests: cada user vê os seus OU admin vê todos
     ("contact_requests_select_own_or_admin"); insert permite user_id NULL ou
     próprio.
   - idem para test_drives ("test_drives_select_own_or_admin").
   - cria bucket storage 'vehicle-images' público + policies (leitura pública,
     escrita/update/delete só admin).
   - revê grants.

6) seed.sql (177 linhas) — Dados de demonstração:
   - 7 viaturas BMW diesel (320d, 420d, 530d, 330d xDrive, X5, 218d, 730d) com
     specs completas, preços, imagens Unsplash e states disponível/reservada/
     vendida.
   - vehicle_features de exemplo.
   - vehicle_images de exemplo (3 fotos da 320d).
   - 6 produtos de loja.
   - site_content (hero/garage/shop/newsletter) com section_keys modernos
     ('hero.tagline', 'hero.slogan', ...) — note: são keys com ponto, que são
     as usadas pelo page.tsx da homepage (lê 'hero.slogan').
   - site_settings (telefone/email/localização/redes).

NOTAS IMPORTANTES / RISCOS CONHECIDOS (schema)
-----------------------------------------------
- Existem DUAS gerações de schema (002_full_site.sql V1 vs setup.sql V2) que
  usam nomes de colunas diferentes. A app atual espera o V2 (vehicle_id,
  site_settings com colunas planas phone/email/..., site_content com keys com
  ponto). O 002_full_site.sql é legacy e deve ser considerado descontinuado.
- A homepage lê site_content com keys "hero.slogan", "hero.intro", "garage.title"
  etc. e usa um FALLBACK em código se não existirem — logo a app funciona mesmo
  sem seed.
- .env.local contém as keys reais (NEXT_PUBLIC_SUPABASE_URL, anon key, e as R2
  vars). O .env.local.example documenta apenas as do Supabase (R2 não está no
  example).

FASE C — AUTENTICAÇÃO, SESSÃO E PERFIS
--------------------------------------

PROXY (proxy.ts — Next 16 substituiu middleware.ts por proxy.ts)
------------------------------------------------------------
- Cria um server client de Supabase com cookies getAll/setAll (padrão SSR do
  Supabase) e faz supabase.auth.getUser() para refrescar/validar a sessão.
- Proteção: qualquer rota que comece por /admin:
  - Sem user → redirect para /conta?redirect=<pathname>.
  - Com user mas role != 'admin' no profiles → redirect para /.
- matcher exclui _next/static, _next/image, favicon e ficheiros estáticos
  (.svg/.png/...).

INFRAESTRUTURA SUPABASE (lib/supabase)
--------------------------------------
- client.ts (browser): createBrowserClient, atira erro dev se faltarem vars.
  Guarda a sessão em cookies (sb-<ref>-auth-token) — o que permite ao proxy
  e às server components autenticarem o mesmo user.
- server.ts: createServerClient com cookies() (next/headers). Usada em todas as
  server components/actions.

LOGIN / REGISTO (app/conta/page.tsx) — Client
---------------------------------------------
- Alterna login/register. No registo pede full_name (mandado via
  options.data.full_name, que o trigger handle_new_user usa para criar o
  profile).
- Login: signInWithPassword → redirecciona para redirect param (ou /).
- Registo: signUp; se o user estiver criado mas SEM sessão (email não
  confirmado), mostra mensagem para verificar o email; senão segue.
- Se já logado (getUser), reencaminha para /conta/perfil.
- Envolvido em Suspense (game de useSearchParams).

CALLBACK AUTH (app/auth/callback/route.ts)
------------------------------------------
- GET com ?code e ?next. Troca o code por sessão (exchangeCodeForSession) e
  redirecciona para next / ou /conta?error=auth em caso de falha.

PERFIL (app/conta/perfil/page.tsx) — Client
-------------------------------------------
- Carrega profile (full_name, email, phone, avatar_url) do user logado.
- Secções:
  1. Definições: avatar (upload via Server Action → R2 → gravado em avatar_url),
     nome (editable), email (disabled), telefone. Guarda via update profiles.
  2. Alterar Password (supabase.auth.updateUser).
  3. Os Teus Pedidos (MyRequests — ver Fase E).
  4. Sidebar: Viaturas Guardadas (FavoritesList) + Zona de Perigo (botão
     "Eliminar Conta" — por enquanto apenas um alert "A implementar").

LOGIN/LOGOUT (header + app/actions/auth.ts)
--------------------------------------------
- Header (client) ouve onAuthStateChange → mostra Backoffice (se admin),
  ícone de perfil, botão Sair; senão botão "Conta".
- logout() é uma Server Action (app/actions/auth.ts): supabase.auth.signOut() +
  redirect("/").

FASE F — MEDIA E ARMAZENAMENTO (CLOUDFLARE R2 + SUPABASE STORAGE)
--------------------------------------------------------------------------------

LIB R2 (lib/r2.ts)
------------------
- Cliente S3Config para Cloudflare R2 (region "auto", endpoint
  https://<ACCOUNT_ID>.r2.cloudflarestorage.com).
- Funções:
  - uploadToR2(key, body, contentType) → URL pública (R2_PUBLIC_URL se
    definida, senão URL .r2.cloudflarestorage.com/<bucket>/<key>).
  - deleteFromR2(key), objectExists(key).
  - getPresignedUploadUrl(key, ct, expiresIn) — URL assinada (não usada ainda
    no front, mas pronta para uploads grandes/diretos).
- Variáveis env: R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY,
  R2_BUCKET (default "vehicle-images"), R2_PUBLIC_URL (opcional).

SERVER ACTIONS UPLOAD (app/actions/upload.ts)
---------------------------------------------
- uploadAvatar(formData): exige user; valida tipo (jpeg/png/webp/gif) e <=5MB;
  key "avatars/<user>-<ts>.<ext>"; upload R2; update profiles.avatar_url;
  revalidatePath /conta/perfil.
- uploadVehicleImages(formData): exige admin; ler files[] (jpeg/png/webp, máx
